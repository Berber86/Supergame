## 1. Стек (сессия 1)

| Слой | Решение | Обоснование |
|---|---|---|
| Код игры | **Vanilla JavaScript, нативные ES-модули** (`<script type="module">`) | Нулевая сборка → нулевая конфигурация деплоя; малый проект, фреймворк не окупается |
| Разметка/стили | **HTML5 + CSS3** (CSS Custom Properties, grid/flex) | Визуал — эмодзи в DOM, canvas не нужен на старте; CSS-грид позже даст «карту-клетки» (вариант B из GDD) без смены стека |
| Графика | Только **эмодзи** как текст | Жёсткое требование README (нет растровой графики) |
| Сборка | **Отсутствует** (no-build) | Vercel отдаёт статику из корня репозитория «из коробки», риск «сломался билд» ≈ 0 |
| Тесты | **Vitest** (devDependency) | Рекомендация README; гоняет чистые ES-модули без транспиляции |
| CI | **GitHub Actions**: на каждый push — `npm ci` + `npm test` | Требование README (тесты на каждый push) |
| Деплой | **Vercel**, автодеплой из `main`, статический сайт из корня репо | Требование README; `vercel.json` не нужен — конфигурация по умолчанию справляется |
| Сейвы (с сессии ~9) | `localStorage` | Без бэкенда/БД — единственный легальный вариант |

### Почему не Vite/React/TypeScript?

- Сборка добавляет точку отказа в пайплайне «push → Vercel» и не даёт
  ничего проекту из эмодзи и DOM.
- Если код вырастет (после сессии 10), миграция ES-модулей в Vite/TS —
  обратимо-совместимая операция; обратной дороги нет только у раннего
  усложнения. Решение пересматриваемо, зафиксировано здесь.

## 3. Ключевые архитектурные принципы

1. **Логика ≠ рендеринг.** Всё в `js/core` и `js/data` — чистые функции и
   данные без DOM/браузерных API. Только это покрывается unit-тестами.
   Слой `js/ui` — тонкий «глупый» рендер.
2. **Детерминированный рандом.** Свой RNG с сидом (mulberry32-подобный)
   в `js/core` — повторяемые тесты, в будущем «дерявая/seed-забеги».
3. **Данные отделены от кода.** Предметы/районы/события — декларативные
   модули в `js/data`; баланс правится правкой данных, а не логики.
4. **Состояние — один plain-объект** (GameState), мутируется только через
   функции-редьюсеры в `js/core`; это упростит сейвы (JSON) и отладку.
5. **Git-поток этой сессии агента:** работа ведётся в ветке
   `arena/019faf3c-supergame` (ограничение среды выполнения агента);
   для автодеплоя на Vercel ветка сливается в `main` (PR открывается
   агентом, слияние — человеком). README предписывает работу в `main` —
   правило среды приоритетнее, расхождение зафиксировано здесь.
6. **Репозиторий никогда не остаётся сломанным:** каждый коммит сессии
   проходит `npm test` локально перед push; CI дублирует проверку.

## 4. Поток данных (будущий, с сессии 4)

```
js/data ──▶ js/core (редьюсеры: действие + state ─▶ новый state, события)
                    │                                   ▲
```

## 5. Риски и как гасим

| Риск | Митигация |
|---|---|
| Эмодзи рендерятся по-разному на ОС/браузерах | CHECKLIST для человека; тестируем базовый набор эмодзи; критичные иконки дублируем текстом |
| Рост кода без фреймворка → хаос | Принципы №1–4 + структура папок; рефакторинг — часть каждой сессии |
| Случайный полом деплоя Vercel | Нет сборки → ломаться почти нечему; корневой index.html всегда валиден |
| Тесты не гоняются из-за package-lock | `npm ci` в CI + lock-файл в репозитории |

## 6. Известные ограничения

- Нет сервера: любые «онлайновые» фичи невозможны по определению.
- iOS Safari исторически капризен к module scripts старых версий — целимся
  в современные браузеры (ES2020+).
